Get to know Wisp.

From opening the app to keeping a collection in Git. Start with a small, working example, then make it your own.

This guide covers the desktop workflow and the collection format used in 0.2.0. Upcoming CLI features are marked separately.

01 / Get Wisp

Open the latest release, download the archive for your platform and the matching SHA256SUMS file, and verify the checksum before unpacking.

PlatformChooseOpen
macOSmacos-arm64.zipWisp.app
Windowswindows-x64.zipwisp.exe
Linuxlinux-x64.tar.gzwisp

macOS requires Apple silicon. Linux requires glibc 2.39 or newer and a working Vulkan driver. See the installation instructions for checksum commands, Linux packages, and release-specific signing details.

On Windows and Linux, a file named portable beside the executable keeps settings and data alongside it. On any platform, an absolute WISP_DATA_DIR overrides the data location. On macOS, use that override for portable data.

02 / Send your first request

  1. Create a folder named hello-api on your machine.
  2. Add the two files below. The example uses the public httpbin test service and needs no credentials.
  3. Open Wisp, choose Open collection, and select hello-api.
  4. Choose Get a response in the sidebar, then click Send.
  5. Inspect the response body, status, and timing. You can edit the request in Wisp and save it back to its TOML file.
hello-api/collection.toml 
format = 1

[vars]
baseUrl = "https://httpbin.org"
hello-api/get-response.toml 
name = "Get a response"
method = "GET"
url = "{{baseUrl}}/get"

[[params]]
name = "hello"
value = "wisp"
enabled = true

The example makes a real request to a third-party test service when you send it from Wisp. The landing page’s interactive preview is a local illustration.

03 / A collection is an ordinary folder

collection.toml marks the root and holds shared defaults. Each request has its own TOML file. Subfolders group requests; an optional folder.toml provides folder defaults and ordering.

A typical collection
hello-api/
├── collection.toml
├── get-response.toml
├── users/
│   ├── folder.toml
│   ├── get-user.toml
│   ├── create-user.toml
│   └── create-user.body.json
├── environments/
│   ├── dev.toml
│   └── dev.secrets.toml   # keep out of Git
└── .gitignore

TOML uses key = value pairs. Strings are quoted, # begins a comment, [vars] starts a table, and [[headers]] starts a new entry in a list. Keys after a table heading belong to that table until the next heading.

Variables and path parameters

Use {{baseUrl}} to substitute a variable. Use {id} in a URL path and define it in [path]. Use [[params]] for query parameters and [[headers]] for headers.

users/get-user.toml 
name = "Get user"
method = "GET"
url = "{{baseUrl}}/users/{id}"

[path]
id = "42"

[[headers]]
name = "Accept"
value = "application/json"
enabled = true

This request is a template for your own API. Update baseUrl to a service that provides a /users/42 endpoint before sending it.

Folder ordering

users/folder.toml 
order = ["get-user.toml", "create-user.toml"]

Keep collection files and body sidecars in Git so changes can be reviewed together.

04 / Switch environments, keep the request

Add environment files under environments/. The filename becomes the environment name. Select it in Wisp before sending.

environments/dev.toml 
[vars]
baseUrl = "https://httpbin.org"

For your own API, add a staging.toml with a different baseUrl. The request can continue using {{baseUrl}}. Keep shared, non-secret values in the environment file.

05 / Inherit auth. Keep secrets separate.

Put shared authentication in collection.toml and let requests inherit it. Wisp supports Basic, Bearer, API key, Digest, AWS Signature V4, and OAuth2. Here is a Bearer example for an API that needs a token.

collection.toml 
format = 1

[vars]
baseUrl = "https://api.example.com"

[auth]
type = "bearer"
token = "{{token}}"
environments/dev.secrets.toml 
[vars]
token = "replace-with-your-local-token"

Select the dev environment so Wisp can resolve its token. Add a plain dev.toml file too; it can contain your environment’s non-secret variables. Keep the secrets file on your machine.

.gitignore 
*.secrets.toml
.wisp-binding
.wisp/
Check the files you stage for a commit. Ignoring a file does not remove it from Git if it was already tracked. Rotate a token if you accidentally publish it.

You can also choose the OS keychain for an environment in Wisp. Secrets files are the default; portable mode and systems without a keychain use a secrets file fallback. The app reports that fallback.

To make inheritance explicit in a request, add [auth] with type = "inherit". To make that request unauthenticated, use type = "none".

06 / Keep bodies alongside requests

For JSON, store the payload in a sidecar file and reference it from the request. This keeps both the request configuration and the payload readable in a diff.

users/create-user.toml 
name = "Create user"
method = "POST"
url = "{{baseUrl}}/users"

[body]
type = "json"
file = "create-user.body.json"
users/create-user.body.json 
{
  "name": "Alex Morgan",
  "role": "developer"
}

The body file must be a plain filename in the same folder as the request. Change the URL and payload to match your API. Sending a POST can create or change data.

07 / Make yourself at home

  • Command palette: press ⌘K on macOS or Ctrl+K on Windows and Linux to find commands, requests, and environments.
  • Save changes: use ⌘S or Ctrl+S. Wisp prompts before discarding unsaved changes during normal quit and tab close. System logout or forced termination can discard drafts, so save before leaving.
  • Bring existing work: use Import for curl commands, Postman v2.1 collections, and OpenAPI 3 JSON or YAML. Read the warnings report; Postman scripts are not translated.
  • Review history: reopen a response or resend a historical request. Resend uses your current environment.
  • Personalise the app: use the command palette to toggle the theme. Personal settings live outside your collection, so they do not become team defaults.

Personal TOML settings

Personal preferences live in settings.toml, separate from collection.toml. Close Wisp before editing this file so the app does not overwrite your change on exit.

settings.toml · preference example 
theme = "dark"      # "system", "light", or "dark"
split = "vertical"  # "vertical" or "horizontal"

Normally this file is under ~/Library/Application Support/wisp/ on macOS, %APPDATA%\wisp\ on Windows, or $XDG_CONFIG_HOME/wisp/ (default ~/.config/wisp/) on Linux. An absolute WISP_DATA_DIR puts it in that directory. Windows and Linux portable mode puts it beside the executable.

When a request does not work

Check that the right environment is selected, each {{variable}} has a value, and each {pathParameter} has a matching entry in [path]. Check inherited auth and enabled headers. For connection problems, inspect the timing panel and confirm the service is reachable.

See the app README for platform details and known limitations, or report an issue.

08 / A foundation for agent workflows

The next step is a read-only CLI with structured JSON: validate a collection, inspect its contents, and explain a resolved request. These commands are under development for the 0.3 direction; they are not part of the 0.2.0 desktop workflow above.

Upcoming CLI · illustrative usage
wisp-cli validate ./hello-api --json
wisp-cli inspect ./hello-api --env dev --json
wisp-cli explain ./hello-api get-response.toml --env dev --json

The planned 0.4 direction adds execution through a shared service layer and redacted context snapshots. MCP integration is deferred, with no committed release date. Follow the development roadmap for the current scope.
